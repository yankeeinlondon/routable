## Prerequisite start-phase instrumentation

Implemented the v1.x metrics prerequisite:

```text
vllm_router_start_phase_duration_seconds{
  service="<configured service>",
  phase="systemd_to_active|active_to_ready|warmup",
  result="success|error"
}
```

The histogram uses the router's existing LLM-scale buckets through 600 seconds
plus Prometheus's `+Inf` bucket. Cardinality is bounded by configured services,
three fixed phases, and two fixed results.

For a cold start, the boundaries are:

1. `systemd_to_active`: entry to the runner's start call through completion of
   the systemd `StartUnit` job. The generated unit is `Type=simple`, so this
   measures supervision/process activation, not model loading.
2. `active_to_ready`: completion of start through the first debounced
   observation that is active, healthy, and advertises the expected model.
   vLLM weight load, compile, graph capture, and its internal warmup occur
   inside this interval.
3. `warmup`: the router's configured one-token HTTP warmup request.

Completed failed phases are recorded with `result="error"`; phases never entered
are not recorded. Wake paths are excluded so cold-start economics are not mixed
with wake timings.

Focused validation:

```sh
cargo fmt --check
cargo test metrics::tests:: -- --nocapture
cargo test cold_start_records_each_successful_phase_once -- --nocapture
cargo test failed_cold_start_records_only_the_failed_completed_phase -- --nocapture
```

All passed. The integration tests establish that a successful cold start emits
each phase exactly once and that a failed start emits only the completed failed
phase.

For each service, run three cold starts of its current TP=1 definition, then
three PP=2 starts with `CUDA_VISIBLE_DEVICES=0,1`,
`--tensor-parallel-size 1`, `--pipeline-parallel-size 2`, the table's exact
`VLLM_PP_LAYER_PARTITION`, and otherwise the identical configured arguments.
Use a dedicated port so the production router cannot route into the experiment.
Before and after each router-owned start, save the metrics scrape. For a run
with one observation, the difference in each matching histogram's `_sum` is
that phase's duration and its `_count` must increase by exactly one:

```sh
curl --fail --silent http://127.0.0.1:6971/metrics \
  > "/tmp/v2-s1-${SERVICE}-${PROFILE}-${RUN}-before.prom"
# Start the cell and wait for the router-owned warmup to complete.
curl --fail --silent http://127.0.0.1:6971/metrics \
  > "/tmp/v2-s1-${SERVICE}-${PROFILE}-${RUN}-after.prom"
rg 'vllm_router_start_phase_duration_seconds_(sum|count)' \
  "/tmp/v2-s1-${SERVICE}-${PROFILE}-${RUN}-"*.prom
```

Do not use the histogram bucket boundary as the duration. Calculate the
per-label `_sum` delta and verify the `_count` delta. Retain all three router
durations: `systemd_to_active`, `active_to_ready`, and the configured HTTP
`warmup`.

For every start, isolate the logs to exactly that systemd invocation and extract
vLLM's distinct model-load and compile reports:

```sh
INVOCATION_ID="$(
  systemctl show --property=InvocationID --value "vllm@${SERVICE}.service"
)"
journalctl --no-pager -o cat \
  "_SYSTEMD_INVOCATION_ID=${INVOCATION_ID}" \
  > "/tmp/v2-s1-${SERVICE}-${PROFILE}-${RUN}.log"
rg -n \
  'Model loading took .* seconds|torch\.compile took .* s in total|init engine .*\(compilation: .* s\)' \
  "/tmp/v2-s1-${SERVICE}-${PROFILE}-${RUN}.log"
sed -nE \
  -e 's/.*Model loading took .* and ([0-9.]+) seconds.*/model_load_seconds \1/p' \
  -e 's/.*torch\.compile took ([0-9.]+) s in total.*/compile_event_seconds \1/p' \
  -e 's/.*init engine .*\(compilation: ([0-9.]+) s\).*/compile_total_seconds \1/p' \
  "/tmp/v2-s1-${SERVICE}-${PROFILE}-${RUN}.log"
```

Preserve the worker/rank prefix on the original matched lines. For PP=2, record
the load duration and compile total for each rank rather than averaging them.
Use the `init engine ... (compilation: N s)` value as vLLM's aggregate compile
duration when emitted; retain the individual `torch.compile took N s in total`
events as supporting detail. If the aggregate is absent, record every compile
event and mark the aggregate `unsupported by vLLM log`; do not silently sum
events that may belong to concurrent ranks or nested compilation stages.

Similarly, if an invocation emits no canonical `Model loading took ... seconds`
line, enter `unsupported by vLLM log`, attach the complete invocation log, and
do not infer load time by subtracting compile or readiness timestamps. Missing
log reports are not zero-second phases. A profile cell remains unresolved if
either required load or compile timing is unsupported and no equivalent
runner-level instrumentation is added.
