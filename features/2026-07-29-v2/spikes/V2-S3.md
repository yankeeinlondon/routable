# V2-S3 — Diffusers runner prototype (Qwen-Image)

Date: 2026-07-29  
Result: **unresolved; no-go on declaring the spike exited.** The HTTP/lifecycle
shape is viable enough to continue runner design, but actual full-pipeline placement,
VRAM, load time, and generation latency remain unmeasured.

## What was established

### Host and model evidence

- Two NVIDIA GeForce RTX 5090 GPUs are visible, each reporting 32,607 MiB.
- The local snapshot at
  `/models/hf/hub/models--Qwen--Qwen-Image/snapshots/75e0b4be04f60ec59a75f475837eced720f823b6`
  occupies 54 GB. Its `model_index.json` names `QwenImagePipeline` and records
  Diffusers `0.34.0.dev0`. All nine transformer shards, all four text-encoder
  shards, and the VAE are present.
- `/root/.venv` has Python 3.12, Torch 2.11.0+cu130, Transformers 5.14.1,
  FastAPI 0.136.3, Uvicorn 0.51.0, and working sm_120 CUDA, but not Diffusers
  or Accelerate. An ephemeral `/tmp` target successfully imported Diffusers
  0.39.0 and Accelerate 1.14.0. No persistent environment was modified.

These facts establish that bring-up needs a separate pinned image-runner
environment; the vLLM executable/environment cannot simply be reused.

### `max_memory` and asymmetric placement

There are two materially different mapping levels:

1. Diffusers pipeline-level `device_map="balanced"` computes the sizes of whole
   pipeline components and assigns a component to one device. It does **not** split
   an oversized component. This is visible in Diffusers 0.39.0
   `_get_final_device_map` / `_assign_components_to_devices`.
2. `QwenImageTransformer2DModel.from_pretrained(device_map="balanced",
   max_memory=...)` delegates at model-module granularity. The class declares
   `QwenImageTransformerBlock` as non-splittable, so its blocks remain placement
   units.

An Accelerate metadata-only probe computed the Qwen-Image transformer at
**40,860,802,176 bf16 bytes**. It accepted and produced different block maps for
asymmetric budgets:

| `max_memory` | Generated transformer map |
|---|---|
| GPU 0 = 8 GiB, GPU 1 = 30 GiB, CPU = 96 GiB | 67 entries: 16 on GPU 0, 47 on GPU 1, 4 on CPU |
| GPU 0 = 20 GiB, GPU 1 = 28 GiB, CPU = 96 GiB | 67 entries: 35 on GPU 0, 32 on GPU 1, none on CPU |

This proves that Accelerate can *plan* an asymmetric transformer split. It does not
prove that the complete pipeline executes correctly or stays within those limits.
In particular, independently mapping the transformer and text encoder against the
same limits can double-spend the GPU budget. The prototype therefore maps the
transformer across the GPUs and conservatively places the text encoder on CPU.
A production planning hook must jointly budget all components and activation
headroom.

One bounded offline weight-load attempt used transformer limits of 20/28 GiB. It
failed in Diffusers' CUDA caching-allocator warmup before dispatch because a
concurrent vLLM spike had begun using 23,382 MiB on GPU 0; only 8.02 GiB was free
when Diffusers tried to reserve 9.52 GiB. This is contention evidence, not a
Qwen-Image placement verdict. No retry was made, to avoid disrupting the other
spike.

### Minimal server and systemd prototype

Artifacts are under `spikes/V2-S3/`:

- `server.py` exposes `GET /health`, `GET /v1/models`, and
  `POST /v1/images/generations`. It serializes generation, validates the requested
  model before inference, and returns OpenAI-style base64 image data. `--mock`
  exercises the contract without weights.
- The real loader explicitly dispatches the transformer with asymmetric
  `max_memory`; it does not use the misleading pipeline-level balanced mapper.
- `qwen-image.service` and `qwen-image.env.example` show the dedicated environment,
  offline model loading, CUDA logical-device ordering, bounded start/stop times, and
  loopback-only server.
- `test_server.py` covers readiness/model discovery, image generation, rejection
  before generation, size validation, and asymmetric-memory parsing.

`systemd-analyze verify` parsed the unit and reported only the expected missing
prototype executable (`/opt/qwen-image-venv/bin/python`); the artifact was not
installed or started.

## Mapping onto the current lifecycle

The repository has two runner seams. `src/runner::Runner` is a vLLM HTTP API
adapter, while `src/pool::Runner` owns `observe/start/stop/sleep/wake/warmup`.
V2-S3 maps to the latter as follows:

| Operation | Diffusers mapping |
|---|---|
| `observe` | Reuse generic systemd and NVML observation; probe `/health`, then verify the configured ID in `/v1/models`. Do not call `/is_sleeping`. |
| `start` | Reuse `SystemdManager::start_unit`; readiness begins only after the pipeline is loaded and the HTTP socket is serving. |
| `stop` | Reuse `SystemdManager::stop_unit`; SIGTERM releases the pipeline/CUDA contexts. This is the only validated idle tier. |
| `sleep` / `wake` | Unsupported; configure no sleep levels. A required trait method can return `sleep_unsupported` defensively. |
| `warmup` | POST a tiny, low-step `/v1/images/generations` request and discard the bytes. It needs image-specific defaults and a much longer timeout than a text token warmup. |

CPU/model offload is **not pseudo-sleep**. Diffusers rejects
`enable_model_cpu_offload()` while a pipeline device map is active, and model
offload is an execution strategy that retains hooks and moves modules during
inference, not an externally observable asleep/wake state. Resetting a device map
moves components to CPU but loses the placement; reconstructing it is effectively a
reload. Until a measured stateful mechanism exists, the idle ladder is
`running -> stopped`.

## Runner and router gaps

1. `RunnerType` has only `Vllm`; validation, argument allowlists, compatibility
   fields, and generated units are all vLLM-specific.
2. `ManagedVllmRunner` constructs a `VllmRunner` for every service. The generic
   systemd/NVML parts need composition with a selected HTTP/capability adapter,
   rather than a second copy of the whole manager.
3. Both runner traits require sleep methods and the managed observer assumes
   `/is_sleeping` when sleep is configured. Unsupported lifecycle capabilities
   need an explicit runner capability contract; Diffusers must validate with an
   empty sleep set.
4. The fixed placement schema requires `TP x PP x DP == gpu count` and one scalar
   VRAM reservation per GPU. Diffusers has none of those parallelism meanings and
   needs per-device budgets plus component/activation headroom.
5. There is no runner planning hook to translate stable GPU UUID budgets into
   Accelerate's logical CUDA indices and `max_memory`, or to decline a placement.
   `CUDA_VISIBLE_DEVICES` ordering is part of that translation.
6. Readiness currently verifies health and model ID, which is reusable, but it
   cannot report load phase, active placement map, or runner capabilities.
7. Warmup configuration is nominally generic, but the vLLM adapter unconditionally
   adds `stream: false`; image warmup needs runner-owned request construction and
   generated-output disposal.
8. The data plane has a global endpoint allowlist and currently rejects
   `/v1/images/generations`. Adding that path globally without a per-service check
   would allow an image request to cold-start a text-only service. Capability
   admission must occur after model extraction and before `choose_running` /
   `ensure_ready`. Replicas sharing a model name must expose a compatible endpoint
   set or selection must become endpoint-aware.
9. Long, non-streaming image requests need an explicit total/generation timeout and
   concurrency limit. The prototype serializes generation but the router does not
   currently model runner capacity.
10. OpenAI image validation includes response formats and image-specific fields.
    Router-generated errors should retain the OpenAI dialect, while the backend
    contract must decide whether URL output/storage, multiple images, and image
    editing are supported.

## Verdict and remaining exit run

**Conditional go** for Diffusers to remain the candidate runner #2: a minimal
OpenAI-compatible server fits the existing systemd/probe/stop mechanics, and a
module-level Accelerate planner can express asymmetric budgets.

**No-go** on claiming V2-S3 complete or committing §4's arbitrary split guarantee.
On an otherwise idle pair of GPUs, the remaining run must:

1. create and pin a dedicated Diffusers/Accelerate environment;
2. load the complete pipeline with a jointly budgeted component plan;
3. record systemd-start-to-health load time and the realized `hf_device_map`;
4. record per-GPU NVML VRAM at ready and peak generation;
5. generate a fixed 1024- or 1328-square image with fixed seed/steps and record
   latency;
6. stop the unit and confirm both CUDA contexts and VRAM are released;
7. optionally compare CPU-offload modes as execution profiles, not sleep tiers.

No load-time, ready-VRAM, peak-VRAM, or generation-latency number is reported here
because none was successfully measured.
