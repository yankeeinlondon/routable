# V2-S5 — GPU power stewardship feasibility (US9)

Date: 2026-07-29 (UTC)

## Exit verdict

**The in-LXC power-limit mechanism is cut.** This LXC can read NVML power
telemetry and constraints, but it cannot write a power limit, even as UID 0.
`nvidia-smi` returned `Insufficient Permissions` for a no-op write of the
already-current 575 W limit on both GPUs. A request to lower empty GPU 0 to its
supported 400 W minimum failed identically. Current and default limits remained
575 W throughout and were verified at the end.

US9 can retain its lifecycle mechanism: stopping the last resident releases the
CUDA context and both GPUs reached P8. The router itself must not promise to
lower an empty GPU's power limit from this container. Doing so would require a
separately designed host-privileged broker/agent; that is a new trust boundary,
not a hidden implementation detail.

**The S5 exit is complete.** Clean 20-second windows now cover both stopped idle
and model-resident idle. On GPU 0, keeping `gptoss20b` resident raised mean idle
draw from 12.309 W to 51.168 W, a 38.859 W difference for these observation
windows. Transient shutdown samples from rejected attempts are not mixed into
either accepted row.

## Watts per lifecycle state

Each accepted row contains 20 samples per GPU from one 20-second wall-clock
window at a target cadence of one sample per second. The reported deviation is
population standard deviation,
`sqrt(mean(power_W²) - mean(power_W)²)`. `nvidia-smi` reported 0% utilization
for every accepted sample. The stopped state had no compute processes and all
four managed model units were inactive. The resident state retained the same
worker PID and exactly 29,658 MiB device memory before, throughout, and after
the sample.

| Lifecycle state | GPU | n / duration | mean W | min–max W | population SD W | VRAM / utilization / P-state | Verdict |
|---|---:|---:|---:|---:|---:|---|---|
| stopped idle | 0 | 20 / 20 s | 12.309 | 12.190–12.560 | 0.094 | 2 MiB / 0% / P8 (20/20) | accepted |
| stopped idle | 1 | 20 / 20 s | 20.214 | 19.120–20.970 | 0.538 | 2 MiB / 0% / P8 (20/20) | accepted |
| model-resident idle (`gptoss20b`) | 0 | 20 / 20 s | 51.168 | 12.350–73.460 | 27.359 | 29,658 MiB / 0% / P1 12, P5 2, P8 6 | accepted |
| model-resident idle control (empty) | 1 | 20 / 20 s | 19.281 | 18.530–20.090 | 0.451 | 2 MiB / 0% / P8 (20/20) | accepted |
| asleep L1/L2 | either | — | — | — | — | sleep is disabled and not hardware-validated for all configured services | not safely runnable |

The same sampler was used after each state's preconditions were established:

```sh
exec 9>/tmp/vllm-router-v2-gpu-spike.lock
flock -n 9
# Stopped window: require no compute processes.
test -z "$(nvidia-smi --query-compute-apps=pid --format=csv,noheader)"
# Resident window: instead require the expected stable worker and >=29,000 MiB
# in five consecutive per-process and per-device observations.
nvidia-smi \
  --query-compute-apps=gpu_uuid,pid,process_name,used_gpu_memory \
  --format=csv,noheader,nounits

timeout 20s nvidia-smi --loop-ms=1000 \
  --query-gpu=index,power.draw,pstate,memory.used,utilization.gpu \
  --format=csv,noheader,nounits
```

The stream was grouped by GPU index with `awk`; for each group it accumulated
`n`, `sum(power)`, `sum(power²)`, minimum, maximum, memory, utilization, and
P-state counts. The explicit 20-second `timeout` was also measured as 20 seconds
by Bash `SECONDS`.

The large difference between the two stopped cards is real for this observation
window, but this one short run does not identify its cause. It must not be
generalized to all RTX 5090s or used as a calibrated board-power value.

The paired empty GPU 1 averaged 0.933 W less during the resident run than during
its earlier stopped-idle window. That small cross-window change does not explain
GPU 0's 38.859 W resident delta. GPU 0 moved among P1, P5, and P8 despite
reporting 0% utilization; residency, not a utilization workload, is the
distinguishing state.

## Accepted request-driven resident run

The successful run exercised the normal data plane rather than starting the
service out of band. With all units stopped and no compute processes, a
`POST /v1/completions` request for `gpt-oss-20b` through port 6969 parked and
triggered the cold start. Attempt 1 returned the expected `503 model_starting`
at its 20-second parking deadline. An immediate retry remained on the normal
request path and returned `200` at 38 seconds with one completion token.

The completed response refreshed lifecycle activity correctly:

```text
lifecycle=running
idle_for=0.013 s
active_requests=0
parked_requests=0
probe.ready=true
```

NVML then reported exactly one worker on GPU 0:

```text
GPU-d751861a-88f6-64c2-8d83-79cf52e0c8ba, 971508, VLLM::Worker, 29648 MiB
```

After the request's utilization transient, five consecutive settle samples had
the same PID, 29,648 MiB per-process memory, 29,658 MiB device memory, 0%
utilization, and zero active/parked requests. All 20 accepted samples retained
29,658 MiB and 0% utilization. After the window, the same worker and memory were
still present, lifecycle remained `running`, and `idle_for` was 25 seconds.

The exact request that supplied lifecycle activity was:

```sh
curl --silent --show-error --max-time 30 \
  -H 'Content-Type: application/json' \
  -X POST http://127.0.0.1:6969/v1/completions \
  -d '{
    "model": "gpt-oss-20b",
    "prompt": "power stewardship resident-idle probe",
    "max_tokens": 1,
    "stream": false
  }'
```

The request was retried immediately after the expected 503. The exclusive
`/tmp/vllm-router-v2-gpu-spike.lock` remained held across both requests,
settling, the 20-second sampler, and the router-owned stop. No power-limit write
was retried.

The accepted run stopped through the router and polled the nested operation
state to success:

```sh
TOKEN="$(</run/secrets/vllm-router-token)"
STOP_ID="$(
  curl --fail --silent --show-error -X POST \
    -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' \
    http://127.0.0.1:6970/pool/v1/services/gptoss20b/stop \
    -d '{"deadline_ms":120000,"force":false}' |
  jq -er '.operation_id'
)"
curl --fail --silent --show-error \
  -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:6970/pool/v1/operations/$STOP_ID" |
jq -er '.state.state'
```

## Rejected resident attempts and lifecycle finding

The first bounded attempt started the normal `vllm@gptoss20b.service` while
holding the GPU-spike lock. It reached `/health` and verified `/v1/models` in
38 seconds. At readiness NVML reported exactly one intended worker on GPU 0:

```text
GPU-d751861a-88f6-64c2-8d83-79cf52e0c8ba, 964947, VLLM::Worker, 29646 MiB
```

That start was issued directly through systemd, outside the router's lifecycle
state machine. The router converged it back to stopped at 12:06:38 UTC. The
nominal sampling window therefore contained teardown: VRAM was 2 MiB and P-state
changed among P0/P3/P5/P8. Its 23.594 W mean is a shutdown transient, **not**
model-resident idle, and is deliberately excluded from the lifecycle table.

A second attempt used the router's authenticated
`POST /pool/v1/services/gptoss20b/start` operation and the start succeeded, but
the sampling harness parsed `.state` instead of the API's nested
`.state.state`. It was stopped and cleaned up without accepting a sample.

The corrected retry reproduced the lifecycle blocker, so it was not looped
again. Operation `806e44d0-31e0-46b3-8e69-8e33a5e5fbce` was polled with
`.state.state` and succeeded in 40 seconds. At that point the router reported
`running`, a healthy/ready probe with two consecutive successes, and zero
active requests. NVML reported one intended worker:

```text
GPU-d751861a-88f6-64c2-8d83-79cf52e0c8ba, 969929, VLLM::Worker, 29648 MiB
```

The first two settle samples retained PID 969929, 29,648 MiB process memory,
29,658 MiB device memory, 0% utilization, and zero active requests. On settle
sample 3 the compute process was gone and device memory was 2 MiB. The router
journal records the start operation succeeding at 12:14:09 UTC and systemd
records shutdown beginning at 12:14:10 UTC.

The cause is an inference supported by live status and the checked-in lifecycle
code: after cleanup, status still reported `idle_for = 20,920 s`, while this
service's `stop_after` is 3,600 s. `Activity::touch` is called by admitted or
parked data-plane requests, but not by a control-plane start. The idle reaper in
`src/pool/mod.rs::reap_idle_once` stops a running service whenever its unchanged
`idle_for >= stop_after`. Thus an operator start of a long-idle service can
complete successfully and be reaped on the next tick before it has a stationary
idle interval. This is also a v1 lifecycle bug/design gap exposed by S5, not a
power-telemetry failure.

Final verification:

```sh
systemctl is-active vllm-router.service vllm@gptoss20b.service
nvidia-smi \
  --query-compute-apps=gpu_uuid,pid,process_name,used_gpu_memory \
  --format=csv,noheader
nvidia-smi \
  --query-gpu=index,power.limit,power.default_limit,memory.used,utilization.gpu \
  --format=csv,noheader
flock -n /tmp/vllm-router-v2-gpu-spike.lock true
```

Result: router `active`; model unit `inactive`; compute-process output empty;
both cards held P8 for three consecutive observations with
`575.00 W, 575.00 W, 2 MiB, 0%`; lock available. The final instantaneous draws
were 12.82 W on GPU 0 and 19.29 W on GPU 1.

## US9 design decision

1. **Mechanism kept:** lifecycle stopping remains the on-box stewardship
   mechanism. An empty stopped card demonstrably reaches P8 and low idle draw;
   the measured GPU 0 mean was 38.859 W below its model-resident idle window.
2. **Mechanism cut:** the router running in CT 107 must not implement direct
   NVML power-limit writes. Readable NVML plus UID 0 does not imply write
   authority. Do not add retries or shell-outs around this permission denial.
3. **Optional alternative, not yet authorized:** a host-privileged broker could
   own power-limit writes and expose a narrow restore-before-placement
   operation. It requires authentication, failure-safe restoration,
   per-GPU serialization, crash recovery, and a host/container trust-boundary
   review. The measured 400 W hardware floor also means a lower limit is
   unlikely to change P8 draw; benchmark before building the broker.
4. **Separate lifecycle finding:** a bare management `start` does not refresh
   activity and can be reaped immediately when the service's previous
   `idle_for` already exceeds `stop_after`. The data-plane path works because
   parked and active request guards touch activity. Fix and regression-test the
   management path separately; it no longer blocks the S5 power measurement.
5. **No remaining S5 run:** the stopped and model-resident idle rows, permission
   verdict, lifecycle delta, and final restoration are all recorded. Sleep
   L1/L2 remains out of scope because it is disabled and not
   hardware-validated for every configured service.

The management-operation polling expression used to diagnose the rejected
control-start attempt was:

```sh
TOKEN="$(</run/secrets/vllm-router-token)"
START_ID="$(
  curl --fail --silent --show-error -X POST \
    -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' \
    http://127.0.0.1:6970/pool/v1/services/gptoss20b/start \
    -d '{"deadline_ms":180000,"evict":false}' |
  jq -er '.operation_id'
)"
curl --fail --silent --show-error \
  -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:6970/pool/v1/operations/$START_ID" |
jq -er '.state.state'
```

That corrected rejected run proved operation polling was not the blocker. Both
it and the final accepted request-driven run used this settle gate:

```sh
nvidia-smi -i 0 \
  --query-gpu=power.draw,pstate,memory.used,utilization.gpu \
  --format=csv,noheader,nounits
nvidia-smi \
  --query-compute-apps=pid,used_gpu_memory \
  --format=csv,noheader,nounits
curl --fail --silent \
  -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:6970/pool/v1/services |
jq -er \
  '.services[] | select(.observed.service=="gptoss20b") |
   .observed.active_requests'
```

It required five consecutive observations with the same worker PID, at least
29,000 MiB resident in both per-process and per-device NVML queries, zero GPU
utilization, and zero active and parked requests. The rejected control-start
run failed residency on its third observation, so its sampler was never
entered. The accepted request-driven run passed all five settle observations
and retained the same residency across all 20 samples and the post-sample
check.

No repository tooling was added: `flock`, `nvidia-smi`, `curl`, and `jq` were
sufficient, and a one-off power-control helper would risk making a denied
privilege look supported.
