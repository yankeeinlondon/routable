# V2-S6 — llama.cpp capability sheet

Date: 2026-07-29  
Result: **conditional go as a deferred optional runner; multi-GPU placement remains
unverified.** A bounded CPU prototype verified the HTTP/readiness contract and
warm-mmap restart behavior. The host had no llama.cpp CUDA binary or CUDA compiler,
so this run does not exit the `--tensor-split` part of the spike.

## Scope and host state

No `llama-server`, `llama-cli`, llama.cpp checkout, or GGUF existed under
`/usr`, `/usr/local`, `/opt`, or `/root` before the spike. The bounded fixture used:

| Item | Pinned value |
|---|---|
| llama.cpp | official Ubuntu x64 release `b10176`; `llama-server --version` reports `10176 (f5b9bd39b)` |
| server archive | 16,430,895 bytes; SHA-256 `dcde63e7eab51da9d4c7589c0ff71c7a92ae4606918864cb8cd0934cea616587` |
| GGUF | `bartowski/SmolLM2-135M-Instruct-GGUF`, revision `09816acd5d99df7be770d85ea30822623dab342c` |
| GGUF file | `SmolLM2-135M-Instruct-Q4_K_M.gguf`, 105,454,432 bytes |
| GGUF SHA-256 | `2e8040ceae7815abe0dcb3540b9995eaa1fa0d2ca9e797d0a635ae4433c68c2d` (matches Hub metadata) |
| host | Linux 7.0.14 x86-64; two RTX 5090s, 32,607 MiB each |
| build constraint | CMake 4.2.3 and GCC 15.2.0 exist; `nvcc` does not |

The initial and final managed state was identical: `vllm-router` active, all four
`vllm@{qwen27b,qwen35b,gptoss20b,gemma31b}` units inactive, both GPUs at 2 MiB
used/P8, and no llama process left running. The shared
`/tmp/vllm-router-v2-gpu-spike.lock` was available at both observations.

The downloaded release is CPU-only (`--list-devices` prints `Available devices:
(none)`), so no GPU-active command was run and the GPU lock did not need to be
held. Downloads and execution remained under a temporary `/tmp` directory; no
package, service, or repository source was installed or changed.

## Reproduce the bounded fixture

The URLs are immutable rather than `latest` aliases:

```bash
SPIKE_TMP=$(mktemp -d /tmp/vllm-router-v2-s6.XXXXXX)

curl -fL --retry 3 \
  -o "$SPIKE_TMP/llama.tar.gz" \
  https://github.com/ggml-org/llama.cpp/releases/download/b10176/llama-b10176-bin-ubuntu-x64.tar.gz
tar -xzf "$SPIKE_TMP/llama.tar.gz" -C "$SPIKE_TMP"

curl -fL --retry 3 \
  -o "$SPIKE_TMP/SmolLM2-135M-Instruct-Q4_K_M.gguf" \
  https://huggingface.co/bartowski/SmolLM2-135M-Instruct-GGUF/resolve/09816acd5d99df7be770d85ea30822623dab342c/SmolLM2-135M-Instruct-Q4_K_M.gguf

sha256sum \
  "$SPIKE_TMP/llama.tar.gz" \
  "$SPIKE_TMP/SmolLM2-135M-Instruct-Q4_K_M.gguf"
```

The server command used for the HTTP and timing probes was:

```bash
"$SPIKE_TMP/llama-b10176/llama-server" \
  --model "$SPIKE_TMP/SmolLM2-135M-Instruct-Q4_K_M.gguf" \
  --host 127.0.0.1 --port 8186 \
  --alias smollm2-spike \
  --ctx-size 512 --threads 4 --gpu-layers 0 \
  --load-mode mmap --slots
```

## HTTP capability evidence

### Readiness and slots

| Probe | Observed behavior |
|---|---|
| `GET /health` | `200`, `Content-Type: application/json`, body `{"status":"ok"}` |
| `GET /v1/models` | `200`; OpenAI-style `data` contains ID `smollm2-spike`, plus llama.cpp's `models` representation |
| `GET /slots` | `200`; JSON array of four idle slots, each with `id`, `n_ctx: 512`, `speculative: false`, and `is_processing: false` |
| `GET /is_sleeping` | `404` with llama.cpp `not_found_error` |
| `POST /sleep?level=1` | `404` with llama.cpp `not_found_error` |

`/health` and `/v1/models` are directly compatible with the current router's
readiness checks. The configured alias is the advertised `data[].id`, so model
verification does not require a llama-specific parser.

The `b10176` help says slots are enabled by default. With explicit `--no-slots`,
`GET /slots` returned `501` and:

```json
{"error":{"code":501,"message":"This server does not support slots endpoint. Start it with `--slots`","type":"not_supported_error"}}
```

Slots are operational telemetry, not a readiness prerequisite. A future adapter
should pin `--slots` explicitly if it consumes this endpoint rather than relying on
an upstream default.

### Inference endpoint matrix

The matrix used one-token, non-streaming requests against the same generation
model. A `200` therefore verifies request/response plumbing, not output quality.

| Router-allowed path | Status | llama.cpp `b10176` behavior |
|---|---:|---|
| `/v1/chat/completions` | 200 | OpenAI chat response |
| `/v1/completions` | 200 | OpenAI text completion |
| `/v1/responses` | 200 | OpenAI Responses-style response |
| `/v1/messages` | 200 | Anthropic-style message response |
| `/v1/messages/count_tokens` | 200 | `{"input_tokens":31}` |
| `/tokenize` | 200 | token array |
| `/detokenize` | 200 | decoded content |
| `/v1/embeddings` | 501 | requires launch with `--embeddings` |
| `/v1/rerank`, `/rerank` | 501 | requires launch with `--reranking` |
| `/v1/score`, `/v2/rerank`, `/v2/embed`, `/score`, `/classify` | 404 | route absent |

This corrects the statement in v2 §1 that llama.cpp does not serve Anthropic
`/v1/messages`: it is false for the pinned `b10176` release. Per-service capability
routing is still necessary, but the capability set depends on the pinned server
version, the model's task, and flags such as `--embeddings`/`--reranking`; runner type
alone is not enough. Admission still must reject unsupported endpoints before
starting a stopped service.

## `--tensor-split` behavior

The pinned CLI exposes:

```text
--split-mode {none,layer,row,tensor}
  layer (default): split layers and KV across GPUs (pipelined)
--tensor-split N0,N1,N2,...
  fraction of the model to offload to each GPU, e.g. 3,1
```

What this run verified:

- a malformed value (`--tensor-split 3,x`) fails before startup with exit code 1
  and `error while handling argument "--tensor-split": stof`;
- the CPU build accepts
  `--gpu-layers all --split-mode layer --tensor-split 3,1` and becomes healthy,
  but lists no accelerator devices and therefore performs no split.

What this run did **not** verify:

- mapping of split positions to the `CUDA_VISIBLE_DEVICES` order;
- realized asymmetric per-GPU weight/KV allocations for `3,1` versus `1,3`;
- whether the 5090/sm_120 CUDA backend builds and executes on this host;
- runtime headroom for the main GPU, compute buffers, and context/KV allocation;
- failure behavior when a requested fraction exceeds a physical GPU's available
  memory.

`--tensor-split` is a relative offload policy, not a hard per-GPU byte limit. The
planner cannot treat its fractions as proof that each ledger budget is respected;
the adapter must compute a candidate split, start it, and validate realized NVML
usage with headroom.

## Warm-mmap restart timing

Five consecutive starts used `--load-mode mmap`. Each trial measured wall time from
process launch immediately before `exec` until the first successful `GET /health`,
then sent SIGTERM and waited for process exit.

| Trial | Launch to health | SIGTERM to exit |
|---:|---:|---:|
| 1 | 133 ms | 15 ms |
| 2 | 133 ms | 14 ms |
| 3 | 137 ms | 15 ms |
| 4 | 141 ms | 15 ms |
| 5 | 138 ms | 15 ms |

Launch-to-health was **133–141 ms, mean 136.4 ms**. llama.cpp's internal log placed
`model loaded` at 125–134 ms. A preceding bring-up after the download measured
141 ms, but that is not a true cold-cache measurement because downloading the file
had already populated page cache.

These numbers establish the mechanism, not production economics: the fixture is a
101 MiB/135M model, uses CPU only, bypasses systemd, and was intentionally
warm-cache. A production GGUF can be orders of magnitude larger, and page-cache
pressure from other models must be included in scheduling cost.

## Current integration implications and gaps

1. `config::RunnerType` has only `Vllm`. `runner_executable` is configurable, but
   the default, compatibility block, validation, and runner-argument allowlist are
   vLLM-specific.
2. The systemd generator always emits `vllm serve`, vLLM parallelism flags,
   `--gpu-memory-utilization`, the multiprocessing executor, and optionally
   `--enable-sleep-mode`. llama.cpp needs a runner-specific argument renderer:
   direct GGUF `--model`, `--alias`, `--load-mode mmap`, `--gpu-layers`, split
   mode/fractions, context/slot settings, and no vLLM subcommand.
3. The low-level `src/runner::Runner` and production `ManagedVllmRunner` are
   vLLM-shaped. Both lifecycle seams require sleep/wake methods, while llama.cpp
   returns 404 for vLLM sleep endpoints. Its validated idle ladder is only
   `running -> stopped`; configure no sleep levels and make unsupported operations
   explicit capabilities/errors.
4. Generic systemd and NVML observation can be reused, but
   `ManagedVllmRunner::from_parts` currently constructs a `VllmRunner` for every
   service. It needs composition with a runner-selected HTTP adapter rather than a
   copied manager.
5. Health, model discovery, systemd start/stop, SIGTERM, and the existing JSON
   warmup shape are reusable. `/slots` can additionally expose active/idle slot
   capacity, but the pool currently models neither runner concurrency nor slot
   saturation.
6. Placement validation currently requires `TP * PP * DP == gpu_uuids.len()` and
   stores one equal VRAM reservation scalar. llama.cpp needs an ordered device list
   plus per-GPU budgets and a runner planning hook that translates them to
   `--tensor-split`. The generated `CUDA_VISIBLE_DEVICES` ordering is the natural
   logical-index boundary, but it must be tested.
7. A split profile must distinguish weights, KV/cache, and non-splittable
   main-device overhead. `--tensor-split` fractions alone cannot satisfy a byte
   ledger or asymmetric fit guarantee.
8. The data plane's single global endpoint list is over-broad for this server:
   several accepted router paths return 404/501, while embeddings/reranking vary
   by launch flag and model. Store an effective capability set per service and
   require compatible endpoint sets for replicas sharing a served model, or make
   replica choice endpoint-aware.
9. Upstream error shapes are already mixed: the verified Anthropic endpoints return
   Anthropic-style success bodies, while unsupported llama.cpp routes return its
   OpenAI-like error envelope. Router-generated pre-admission errors should continue
   using the request path's dialect.
10. Scheduling restart cost must be runner/profile-specific. Warm mmap makes the
    GGUF page-cache state materially different from a true disk-backed cold start,
    and `--mlock`/non-mmap modes would change both host-memory accounting and
    restart behavior.

## Verdict

**Conditional go, remain deferred optional.** llama.cpp fits the router's basic
systemd/health/model/warmup/stop contract, its current API surface is broader than
the spec assumed, and the tiny warm-mmap result supports investigating fast
stop/restart as its only idle ladder.

Do not promote it to runner #2 or claim V2-S6 exited yet. The load-bearing
asymmetric-GPU claim is still based only on CLI surface, not a CUDA measurement.
Diffusers priority can be decided independently; llama.cpp implementation should
wait for the remaining run below.

## Remaining lock-protected CUDA run

Use a CUDA-enabled build of the same pinned llama.cpp commit and a GGUF large enough
that the split is visible above CUDA/context overhead. Do not install a CUDA toolkit
or download a large model merely to complete this spike; point `LLAMA_SERVER` and
`GGUF` at prepared artifacts.

```bash
exec 9>/tmp/vllm-router-v2-gpu-spike.lock
flock -x 9

LLAMA_SERVER=/absolute/path/to/cuda/llama-server
GGUF=/absolute/path/to/test-model.gguf
PORT=8186

initial_units=$(systemctl is-active \
  vllm@qwen27b vllm@qwen35b vllm@gptoss20b vllm@gemma31b || true)
nvidia-smi --query-gpu=index,uuid,memory.used,pstate \
  --format=csv,noheader
"$LLAMA_SERVER" --version
"$LLAMA_SERVER" --list-devices

CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=0,1 \
  "$LLAMA_SERVER" --model "$GGUF" \
  --host 127.0.0.1 --port "$PORT" --alias llama-split-spike \
  --gpu-layers all --split-mode layer --tensor-split 3,1 \
  --load-mode mmap --slots
```

For each of `3,1`, `1,3`, and `1,1`:

1. require both CUDA devices in `--list-devices`;
2. poll `/health`, verify `/v1/models`, and record launch-to-health;
3. retain the full server log, including per-device buffer/offload lines;
4. record per-process used memory by GPU with
   `nvidia-smi --query-compute-apps=pid,gpu_uuid,used_memory --format=csv`;
5. issue a fixed prompt at the production context target, then record peak VRAM;
6. SIGTERM the process, require its PIDs and VRAM to disappear, and repeat five
   warm-mmap restarts;
7. restore every initially active managed unit and compare final unit/GPU state to
   the captured initial state before releasing file descriptor 9.

The split passes only if reversing `3,1` measurably reverses weight allocation in
the `CUDA_VISIBLE_DEVICES` order, all three profiles stay within explicit per-GPU
budgets including inference peak, and every restart/stop releases CUDA ownership.
