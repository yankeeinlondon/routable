# V2-S4 — Add-only registration seam probe

Date: 2026-07-29  
Scope: code/design spike only; no registration endpoint is exposed

## Verdict

**Conditional go, but §2's “additive is easy” claim is too strong as written.**

Add-only publication does avoid the stale-consumer invalidation problem: immutable
`Arc<RouterConfig>` snapshots work, existing pool entries and semaphores never need
replacement, and the v1 placement scheduler has no separate participant index to
invalidate. The prototype confirms that a candidate can be cloned into the live
configuration, passed through the complete existing `RouterConfig::validate`, and
published atomically while current readers finish on their old snapshot.

End-to-end registration is nevertheless a medium-sized coordinated transaction, not
a map insertion. The managed runner, generic pool, state store, generated inputs, and
systemd manager must be prepared before the config becomes visible to ingress. Failure
ordering and concurrent registrations need one writer/coordinator.

There is also one correctness counterexample to unrestricted add-only registration:
adding a **replica of an existing canonical model with a new alias** is not operationally
additive. Generated units give every replica the union of aliases, while ingress
forwards the request body unchanged. `daemon-reload` does not teach an already-running
vLLM process the new served name, so the router could select an old replica that rejects
the newly published alias.

Until ingress canonicalizes the forwarded model field, registration should permit:

1. a new canonical model and its aliases; or
2. a new replica whose aliases are a subset of the existing canonical model's live
   alias set.

Reject alias expansion for an existing canonical model with a registration-specific
validation error. Restarting existing replicas to add the alias would contradict the
non-disruptive/add-only premise.

## Prototype evidence

The spike changes three source/test files and intentionally stops short of a control
API:

- `ConfigStore` now holds an `RwLock<Arc<RouterConfig>>`. `snapshot()` remains cheap
  and immutable for a reader. `register_service()` serializes writers, clones the
  current snapshot, appends exactly one candidate, calls the same full `validate()`
  used at boot, and only then swaps the `Arc`.
- A rejected merged configuration leaves the live snapshot untouched. A successful
  addition becomes visible to canonical/alias lookup while an earlier `Arc` remains
  unchanged.
- `DataPlane`'s per-canonical-model parking map is now additive. It preserves every
  existing semaphore (and therefore all outstanding permits) and lazily inserts one
  semaphore after a newly published canonical model reaches admission.
- Alias routing was not another stored boot map: `alias_map()` is already rebuilt
  from the operation's config snapshot for each inference request. Making
  `ConfigStore` swappable is sufficient.
- `/v1/models` was not separately frozen either: `configured_models()` is already
  computed from the request's config snapshot.

The publication method is explicitly marked as the spike seam. It does no systemd,
runner, or pool work and is therefore unsafe to wire directly to an endpoint. The
production coordinator must invoke config publication as its final infallible commit.

Tests added:

- `config::tests::additive_registration_validates_the_merged_config_before_publication`
  demonstrates an alias conflict rejected by the existing full validator, no partial
  publication, a valid second service, live alias resolution, and immutable old
  snapshots.
- `proxy::ingress::tests::additive_config_publication_gains_model_discovery_and_parking_capacity`
  demonstrates that an already-constructed data plane sees the newly published model
  in discovery and creates parking capacity without replacing the data plane.

Prototype source/test diff (excluding this note): **146 insertions, 26 deletions**
across `src/config/mod.rs`, `src/config/tests.rs`, and `src/proxy/ingress.rs`. Much of
the apparent ingress churn is the focused test and formatting.

## Exact frozen-seam inventory

| Area | Current boot-frozen structure | Required additive treatment |
|---|---|---|
| Configuration | `ConfigStore.current` was one `Arc<RouterConfig>` | Swappable immutable snapshots; serialize registration writers; validate candidate against a clone of the latest live snapshot; publish last. Prototyped. |
| Alias routing | No persistent alias map: `alias_map()` derives a `HashMap` from the request snapshot | No extra registry required after config snapshots become swappable. Consider a precomputed immutable index later for cost, not correctness. |
| Model discovery | `configured_models()` derives `/v1/models` from the request snapshot | No extra registry required. Prototyped through the live-store test. |
| Data-plane parking | `DataPlane.model_parked: HashMap<canonical, Arc<Semaphore>>` constructed once | Mutable/additive map that never replaces an existing semaphore. Lazy insertion is safe because only a fully resolved configured canonical reaches parking. Prototyped. The global semaphore remains fixed because registration cannot change top-level policy. |
| Generic pool | `PoolInner.services: HashMap<name, Arc<ServiceEntry>>` | Additive `RwLock`/copy-on-write registry. Commit a fully built `ServiceEntry` containing definition, activity counters, admission/flight locks, and backoff counters. Every lookup/iteration must take a short snapshot so no lock spans `.await`. |
| Observed state | `StateStore.services` is already an `RwLock<HashMap<...>>`; `register()` already adds a watch channel | No structural change. Pool registration must call it exactly once as part of the pool commit and must reject duplicate service names before doing so. |
| Placement participants | There is no second placement table in v1 | The participants are exactly `PoolInner.services`. Overlap checks, the placement queue, blocker/victim selection, status, `reconcile_all`, and idle reaping all consult that map. Once its iteration snapshots are additive, the new entry participates automatically. The per-demand placement queue itself needs no registration. |
| Managed runner | `ManagedVllmRunner.services: HashMap<name, ManagedService>` | Additive registry of `Arc<ManagedService>`. A prepared entry includes the cloned config, vLLM HTTP adapter, probe debounce, systemd observation, sleep provenance, and GPU-warning state. `expected_gpu_state()` must snapshot this registry so the service also joins drift/accounting expectations. |
| Generated inputs | `install_generated_inputs()` validates/renders **all** services, then atomically replaces each unit/environment file separately | Add a render/prepare API for the candidate using the already-validated merged config (needed for the canonical alias union), then install its two outputs before reload. The current multi-file install is not an atomic set and has no rollback; an orphaned, unschedulable candidate file is an acceptable retry artifact, but config must remain unpublished. Do not rewrite all existing units for a simple addition. |
| systemd visibility | `ManagedVllmRunner::connect()` installs all inputs and calls `SystemdManager::reload()` once | Registration coordinator must await candidate file installation and `reload()` before committing runner/pool/config visibility. Prebuild all fallible in-memory adapters first. |
| GPU-index render input | NVML UUID→CUDA index map is constructed in `ManagedVllmRunner::connect()` and discarded after boot generation | Retain/recompute this mapping for candidate rendering and re-check that every configured UUID is still present. |
| Systemd timeout | One `SystemdManager.timeout` is chosen as the maximum initial `systemd_job_ms` | A candidate can request a longer deadline than the frozen manager timeout. Either make timeout an operation argument or reject a candidate above the boot ceiling. This is a hidden registration constraint. |
| Control plane | Only `GET /pool/v1/services` and per-service lifecycle `POST`s exist; `ControlPlane` has config and `dyn PoolManager`, but no registrar | Add an authenticated `POST /pool/v1/services` before the existing action route, strict body parsing, conflict/validation/system error envelopes, and a dedicated registration coordinator/trait. Do not put the transaction piecemeal in the HTTP handler. |
| Pool facade | `PoolManager` exposes lifecycle/status/admission only | Keep registration separate (for example `ServiceRegistrar`) or add an object-safe registration request. Production needs access to both `ManagedVllmRunner` and `Pool`; the current facade cannot update the runner map. |
| Background cadence | `PoolBackground` computes one observation interval from the boot config | A newly registered service with a shorter readiness interval will not change the ticker. Read the minimum from the live snapshot or define a fixed process cadence. This affects observation promises, not map correctness. |

Listeners, auth token, upstream client policy, global parking policy, inventory, and
top-level environment remain process-level configuration. The registration payload
must be a `ServiceDefinition`, not a replacement `RouterConfig`, so it cannot mutate
them.

## Recommended production transaction

Use one async mutex/single writer around these steps:

1. Snapshot the latest live config; reject an existing service name.
2. Clone it, append the candidate, and run the complete existing validator.
3. Run the additional existing-canonical alias-subset rule.
4. Prepare all fallible in-memory values: managed runner adapter, generic pool
   definition/entry, generated unit and environment bytes, and current GPU index map.
5. Atomically install the candidate's generated files and await systemd
   `daemon-reload`.
6. Commit the managed-runner entry, pool entry, and state channel with commit methods
   designed not to fail after their prechecks. The service is still invisible to
   ingress because config has not been published.
7. Publish the already-validated `Arc<RouterConfig>` in `ConfigStore`. Existing
   ingress operations finish on their earlier snapshots; new operations can route to
   the service and lazily acquire its model semaphore.
8. Return `201 Created` with the desired definition and initial observed state.

Before step 7, a failure leaves the old runtime behavior intact. Generated files may
remain as inert retryable artifacts. After step 7 there must be no fallible work.
Concurrent registration is serialized so a prepared merge cannot overwrite a service
published by another writer.

Crash consistency is a separate product decision. Because runtime configuration is
currently in memory, a successful registration disappears on router restart unless
the single control-plane writer also persists the authoritative service inventory.
§2 says definitions become control-plane-owned data; the v2 plan must name that durable
store and recovery order.

## Production diff-size estimate

Expected implementation, excluding durable-store/UI work:

- mutable config/data-plane registries and indexes: 80–140 lines;
- pool/state/managed-runner additive commit seams: 180–300 lines;
- candidate-only unit rendering/install plus coordinator and errors: 220–350 lines;
- authenticated control endpoint: 100–170 lines;
- unit, concurrency, rollback-order, and HTTP tests: 300–500 lines.

**Estimated total: 880–1,460 gross changed lines across roughly 8–11 files.** The lower
end assumes the alias-subset restriction. Canonical body rewriting, persistence, or
strong multi-file rollback would be separate work and push the change beyond this
estimate.

## Explicit gaps and limitations

- No `POST /pool/v1/services` exists.
- The prototype does not update `ManagedVllmRunner`, `Pool`, or `StateStore`; a
  prototype-published service is discoverable but cannot run. The method is not wired
  into production.
- No unit is generated and no daemon reload occurs in the prototype.
- No persistence or restart recovery is designed.
- No concurrent-writer, crash, or injected filesystem/systemd failure test exists.
- The alias-expansion restriction is documented but not implemented.
- The live-host systemd/NVML path is not exercised by this code-only spike.
