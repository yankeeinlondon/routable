# V2-S2 — Co-residency interference curves

Date: 2026-07-29 UTC

## Exit verdict

**Not exited; blocked at profile feasibility.** No latency or throughput curve is
reported because the example pair in the spec did not fit on one RTX 5090 under the
tested profiles. Reporting solo numbers without a runnable co-resident case would not
answer the spike.

The actionable result is that `gpt-oss-20b at low utilization + qwen27b` must not be
used as the V2-S2 pair with the current qwen service shape:

- qwen27b at `gpu_memory_utilization=0.58`, `max_model_len=4096` loaded 18.85 GiB of
  model memory but reported **-3.12 GiB available KV cache**, then exited.
- gpt-oss-20b at `gpu_memory_utilization=0.42`, `max_model_len=4096` loaded 13.8 GiB
  of model memory but reported **-2.25 GiB available KV cache**, then exited.
- The GPU total visible to torch was 33,670,758,400 bytes (31.35 GiB). Adding the
  missing memory to each requested fraction gives approximate zero-KV floors of
  `0.58 + 3.12/31.35 = 0.680` and `0.42 + 2.25/31.35 = 0.492`. Their sum is about
  **1.17 before allocating usable KV cache**, so this pair cannot co-reside on one
  card in these shapes.

This is a profile-specific result, not a claim that no pair can share the card.
Select a genuinely packable pair (or explicitly validate a smaller,
language-model-only qwen profile) before running the curve matrix below.

## MPS verdict

**Container permission/control-plane: pass. vLLM runtime/performance: unproven.**

The MPS control daemon successfully started with private pipe/log directories inside
the LXC, enumerated the selected RTX 5090, and accepted `quit` with status 0:

```bash
mps_tmp_dir=$(mktemp -d /tmp/v2-s2-mps.XXXXXX)
export CUDA_VISIBLE_DEVICES=GPU-d751861a-88f6-64c2-8d83-79cf52e0c8ba
export CUDA_MPS_PIPE_DIRECTORY="$mps_tmp_dir/pipe"
export CUDA_MPS_LOG_DIRECTORY="$mps_tmp_dir/log"
mkdir -m 700 "$CUDA_MPS_PIPE_DIRECTORY" "$CUDA_MPS_LOG_DIRECTORY"
nvidia-cuda-mps-control -d
printf 'get_server_list\ndevice_query --csv\nquit\n' |
  nvidia-cuda-mps-control
```

`device_query --csv` returned:

```text
0,0000:c1.00.00,GPU-d751861a-88f6-64c2-8d83-79cf52e0c8ba,NVIDIA GeForce RTX 5090,
```

This proves that the unprivileged container can create and control an MPS daemon. It
does **not** prove that vLLM workers attach to MPS or that MPS improves isolation.
That verdict requires two healthy co-resident vLLM servers plus live
`get_client_list` evidence during the MPS matrix.

## Reproducible remaining experiment

### 1. Select and freeze a packable profile pair

Use two distinct configured models if possible. For every candidate profile:

1. Run it solo with the exact intended production flags.
2. Require `/health` success and record vLLM's model-memory and available-KV lines.
3. Require enough KV for the fixed 256-input/64-output load at the maximum tested
   concurrency; a merely positive single cache block is not sufficient.
4. Require `utilization_A + utilization_B <= 0.95` to retain at least 5% headroom.
5. Start both on the same physical GPU and require both health endpoints to remain
   healthy for five minutes before collecting a result.

If qwen is made `--language-model-only`, treat that as a new declared placement
profile and separately verify that it matches the intended endpoint capabilities.
Do not silently substitute it for the current multimodal-capable service.

### 2. Freeze load and repetitions

- Dataset: vLLM random
- Seed: 20260729
- Input/output: 256/64 tokens
- Requests per cell: 48, after 8 warm-up requests per server
- Concurrency points: 1, 2, 4, 8
- Repetitions: 3 per cell; report median repetition and its raw JSON
- Percentiles: p50, p95, p99 for TTFT, TPOT, inter-token latency, and end-to-end
- Temperatures/sampling parameters must be identical across every cell

Example collection command:

```bash
/root/.venv/bin/vllm bench serve \
  --backend openai --base-url http://127.0.0.1:18100 \
  --endpoint /v1/completions --model MODEL_A \
  --dataset-name random --random-input-len 256 --random-output-len 64 \
  --num-prompts 48 --num-warmups 8 --request-rate inf \
  --max-concurrency 4 --seed 20260729 \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,95,99 \
  --save-result --result-dir RESULTS_DIR \
  --result-filename off-solo-a-c4-r1.json
```

For co-resident cells, start the two benchmark commands concurrently, record one JSON
per model, and wait for both. Do not benchmark A and then B sequentially and label it
co-resident load.

### 3. Matrix

| MPS | Residency/load | A concurrency | B concurrency | Purpose |
|---|---:|---:|---:|---|
| off/on | A solo | 1,2,4,8 | 0 | A baseline |
| off/on | B solo | 0 | 1,2,4,8 | B baseline |
| off/on | balanced co-resident | 1,2,4,8 | 1,2,4,8 | symmetric contention curve |
| off/on | A foreground | 1 | 1,2,4,8 | A latency-priority sensitivity |
| off/on | B foreground | 1,2,4,8 | 1 | B latency-priority sensitivity |

Before every MPS-on server start, start a fresh daemon and export its pipe directory
into both vLLM server environments. While both servers are loaded and while both
benchmarks are active, save:

```bash
printf 'get_server_list\nps\nget_device_client_list\n' |
  nvidia-cuda-mps-control
nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory \
  --format=csv,noheader
```

An MPS-on result is invalid unless both vLLM worker PIDs appear as MPS clients.

### 4. Derive the curves and exit

For each model, load point, percentile, and MPS mode calculate:

```text
degradation_ratio = co_resident_metric / solo_metric
throughput_ratio  = co_resident_output_tokens_per_second /
                    solo_output_tokens_per_second
```

Retain the raw JSON and report median plus repetition spread. The spike exits only
when:

- a healthy, memory-safe co-resident pair has completed every matrix cell;
- latency/throughput degradation curves exist for both models;
- MPS worker attachment is evidenced, or MPS runtime failure is captured with logs;
- the recommendation explicitly says whether `max_awake_owners_per_gpu` may be
  relaxed, and under which latency-priority/admission thresholds.

Until then, keep `max_awake_owners_per_gpu: 1`.
